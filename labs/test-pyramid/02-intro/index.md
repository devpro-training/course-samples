# Automated testing, the test pyramid

Write the three kinds of tests of a web API, and see what each one catches.

---

## Why automate tests

- A test is a program that runs another program and **fails when the result is wrong**.

- It runs in seconds, on every change, on every machine, and in the CI pipeline.

- It makes a change safe: a broken behavior is found by the test, not by a user.

- It documents what the code is supposed to do, with examples that cannot go out of date.

## Three layers

Layer      | Exercises                                             | Speed       | A failure points to
-----------|-------------------------------------------------------|-------------|--------------------
Unit       | One class or method, with its dependencies replaced   | Milliseconds | The line of code
Integration | Several components together, with real ones          | Under a second | A wrong wiring or a wrong contract
End-to-end | The whole application, through its user interface     | Seconds     | Something, somewhere

- The idea is from Mike Cohn, in *Succeeding with Agile*: unit, service and UI tests.

- Its rule: write tests with different granularity, and the more high-level they get, the fewer there should be.

- Martin Fowler's [Practical Test Pyramid](https://martinfowler.com/articles/practical-test-pyramid.html) adds that the names matter less than the trade-off.

---

## What Microsoft says

- A **unit test** exercises a single method or class, and does not test infrastructure: databases, file systems, network resources.

- An **integration test** checks that two or more components work together, and often includes infrastructure.

- Integration tests are slower and take more code, so "if a behavior can be tested using either a unit test or an integration test, choose the unit test".

Source: [Testing in .NET](https://learn.microsoft.com/dotnet/core/testing/) and [Integration tests in ASP.NET Core](https://learn.microsoft.com/aspnet/core/test/integration-tests), on 2026-10-07.

## Fake, mock, stub

- A **test double** replaces a dependency during a test, so the unit is tested alone and the result does not depend on the clock, the network or a database.

- A **fake** is a simple working replacement, a class written for the test.

- A **mock** is generated by a library, which also records how it was called.

- The lab uses fakes only: no library, nothing hidden.

Step             | What

Unit test        | xUnit, and a fake for the sale
Integration test | `WebApplicationFactory`: the API in memory, called over HTTP
