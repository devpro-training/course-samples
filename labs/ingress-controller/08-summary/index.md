## Cheat sheet

Task                    | Command
------------------------|-----------------------------------------------------------------------------------
Classes and controllers | `kubectl get ingressclass`, `kubectl get gatewayclass`
Ingresses and routes    | `kubectl get ingress`, `kubectl describe ingress <name>`, `kubectl get gateway,httproute`
Test a rule             | `wget -qO- http://<host>:<port>/<path>`, `--content-on-error` to see an error body
Look at a certificate   | `openssl s_client -connect <address>:443 -servername <host> < /dev/null \| openssl x509 -noout -subject -issuer -dates`
Make a certificate      | `openssl req -x509 -newkey rsa:2048 -nodes -days 30 -keyout <key> -out <crt> -subj "/CN=<host>" -addext "subjectAltName=DNS:<host>"`
TLS Secret              | `kubectl create secret tls <name> --cert <crt> --key <key>`
Certificates            | `kubectl get certificate`, `kubectl describe certificate <name>`
Trust an authority      | `wget --ca-certificate <ca.crt> https://<host>/`

## Where things are

What                       | Where
---------------------------|----------------------------------------------------------------------------
The controller of k3s      | The Deployment `traefik` of `kube-system`, installed by a Helm chart
Its configuration          | A `HelmChartConfig` named `traefik` in `kube-system`
Its entry points           | `web` and `websecure`, ports 8000 and 8443 in the Pod, 80 and 443 on the Service
The default certificate    | Generated by Traefik, `TRAEFIK DEFAULT CERT`
A Traefik middleware       | `traefik.io/v1alpha1`, named `<namespace>-<name>@kubernetescrd` in an annotation
cert-manager               | The namespace `cert-manager`, with the Secret of a `ClusterIssuer` of type `ca`
Certificates it issued     | The `Certificate` and the Secret named by the `tls` section
Gateway API definitions    | CRDs of `gateway.networking.k8s.io`, with their release in the annotation `bundle-version`

## Tips

- **Name the class**: `ingressClassName` on every Ingress, even when a default exists, so a second controller changes nothing.

- **One host, one certificate, one Secret**: each Ingress that asks cert-manager for a certificate has its own `secretName`.

- **Test the whole path**: name, port, certificate and application, with the same names a client uses.
  A `Host` header sent by hand does not test the certificate.

- **Read the status**: `kubectl describe ingress`, the `Certificate` conditions, and the `Accepted` and `Programmed` conditions of a Gateway say why nothing answers.

- **Keep the annotations in one place**: each one ties the Ingress to a controller, so a list of them is the migration plan.

- **Start with the staging authority** when using ACME: a mistake costs nothing, and the rate limits stay untouched.

## Good practices

- Redirect HTTP to HTTPS at the controller, and never switch the verification off in a client to make a test pass.

- Give the private authority a short life per environment, and distribute its certificate to the clients that must trust it.

- Do not put the private key of a certificate in a repository: cert-manager creates it in the cluster, and a Secret that must be in a repository is encrypted first.

- Pin the version of the controller and of the Gateway API definitions, and read the release notes before an update.

- Plan the move to the Gateway API: new applications can start with routes, and the Kubernetes blog announced Ingress2Gateway 1.0 as a path from the existing Ingresses.

- Expose as little as possible: an internal application stays on a `ClusterIP`, with no Ingress.
